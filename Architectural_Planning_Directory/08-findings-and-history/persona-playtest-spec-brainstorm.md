# Persona Playtest & Spec Brainstorm

**Date:** 2026-09-27  
**Surface:** running Veritas Gold website at `http://localhost:5173/`  
**Method:** Real-browser UI, safe/non-mutating checks only. No order, transfer, approval, issuer, or settlement action was submitted.

## Playtest Summary

At the time of this playtest, eight personas were configured in `PERSONA_LIST`; the user subsequently decided the Executive Signer & Mobile Approver persona is not needed, leaving seven. It was selected and its old mobile surface tested before removal. The app visibly changes the active persona title, but workstation selection leaves the same Master Admin Radar, participant directory, all-module sidebar and platform action ribbon on screen. This proves the observed UI is persona labeling/impersonation, not role-scoped workspaces or an access-control boundary. The UI already starts authenticated as Super Admin without requiring the login flow.

The default app state in `App.tsx` is already `PERSONA_LIST[0]` (Platform Super Admin), so it starts without authenticating. The login surface presents 8 personas, four direct test portals, SANDBOX/DEMO/PRODUCTION selection, backend selectors, authentication protocol buttons and credential fields, but these controls do not authenticate/connect to the claimed systems: credential fields are readonly/hardcoded/masked, database choices are static, auth protocol only updates local UI state, and the authorization button waits through a simulated sequence. Production is selectable even though no production backend or payment rail is configured. No backend role/session token was observed.

## Defects / Confusions Observed (Severity Order)

1. **Critical for any real authorization claim — client persona switching does not scope or authorize access.** Admin “Switch Role” updates persona text/toast only; same Admin routes/actions remain. Login starts pre-authenticated as Super Admin, and “authentication” is a timed client animation. A user could mistake impersonation for real authorization. This must be resolved before deploying as anything beyond a clearly marked public sandbox.
2. **High — mobile cash and approvals contradict the backend and each other.** €2.45m synthetic cash vs two zero-settled EURD API accounts; 0 pending badge vs two pending checker tickets and zero inbox badge. In addition, `localApprovals` copies `initialApprovals` once into local React state and does not follow subsequent prop refreshes, so it can drift. Do not use for financial decisions.
3. **High — demo/production environment switch is only presentation state.** Production is selectable on login despite current app using seeded in-memory records and no rails. The top UI may color non-sandbox values green. Clear environment semantics and safe disablement are needed.
4. **High — admin KPIs/claims are internally inconsistent or unsupported.** “8 institutions” vs “7 Institutional Nodes Active”; all-KYC-cleared, multi-bank aggregates and “zero double-spend guarantee” are shown without evidence from the live API. The user cannot tell fixture claims from measured telemetry.
5. **High — auditor clearance is not read-only.** The Auditor retains same Admin controls/navigation; no view-only enforcement or audit-specific purpose limitation.
6. **Medium — persona context does not carry into runtime mode.** Selecting Executive from the participant directory does not switch to its configured default mobile surface; users have to reopen the authentication selector and authorize again.
7. **Medium — role chooser and test logins imply real institution credentials.** Named real institutions, BIC/LEI-like identifiers, readonly signer IDs, “FIPS 140-2”, “FIDO2”, mTLS and “10-Yr GDPR” labels appear alongside static values. Labels should identify fixtures and non-integrated controls explicitly.
8. **Medium — no role-specific onboarding or day-one task path.** Seven workstation roles fall into same admin page; there is no clear “what can I do next” or representative role workflow. Mobile has separate areas but hardcoded demo operations.

## Structural Health Observed

- `frontend/src/components/auth/InstitutionalLoginSurface.tsx` defines the persona list and login/target-mode showcase UX.
- `frontend/src/components/admin/MasterAdminOverview.tsx` owns global radar fixtures and renders impersonation buttons.
- `frontend/src/App.tsx` initializes an already-authenticated Super Admin, switches only `authenticatedPersona` for admin role clicks, routes all personas to shared global navigation, and separately controls runtime mode.
- `frontend/src/components/mobile/InstitutionalMobileSurface.tsx` owns mobile tabs, locally copied approvals, sample purchase asset data, and client-only approve/reject actions.
- `frontend/src/components/smart/Sidebar.tsx` contains the workstation persona dropdown and the common all-feature navigation tree.
- This crosses role/session, global KPI fixtures, mobile approval state and shared navigation. UI-level role changes are too shallow to enforce policies. Current mobile approval behavior combines mock workflow state directly into a very large presentation component (~1,200 lines); it belongs in an explicitly sandbox-scoped data/workflow service with consistent API source before using it as a real signer UX.

## Spec-Brainstorm: Ranked Feature Enhancements

Costs are relative engineering estimates, not guarantees. These features stay within the platform’s stated meaning as an institutional workflow/recordkeeping/orchestration prototype; no idea should be presented as a live settlement rail absent integration and approval.

| Rank | Enhancement | Why demanding users notice | Rough cost |
|---:|---|---|---|
| **1** | **Persona-safe, source-of-truth demo workspaces** — define per-persona capabilities and route menus; remove pre-authenticated root default; make role switching explicitly a sandbox persona preview; unify shared mobile device-view data with API-backed or clearly labeled fixture data; hide or disable production mode until a real environment exists. | Stops the Admin controls showing up for the auditor/bank and prevents fabricated cash/order counts from looking operational. Gives each of the seven retained personas a credible “what I can do” surface. | **M–L** (policy model + nav composition + data reconciliation + regression checks across 7 roles) |
| **2** | **Evidence-backed operational status & data provenance** — each dashboard tile records source, as-of time, environment and “live API / static demo / unavailable”; replace unsupported AUM, KYC, quorum/finality claims with measured data or conspicuous fixtures. | Operators and auditors can challenge numbers and reconcile stale/missing feeds; the dashboard stops presenting demo KPIs as verified infrastructure. | **M** (data contracts, provenance metadata, component updates, freshness/empty-state coverage) |
| **3** | **Institutional approval case file** — show amount/currency, account before/after headroom, maker, mandate, policy checks, supporting evidence, signatures needed, expiry and a human-readable decision trail; approval remains sandbox-only and non-mutating until a service implements it. | Authorized institutional operators need to know exactly what they are reviewing and why. Keep approval as a capability within the relevant retained bank/central-bank roles, not as a separate Executive Signer persona. Current mobile shows large-value fake tickets, inconsistent counters and no durable rationale/evidence. | **M–L** (approval domain schema, desktop/device-view workflow, audited decision record, tests) |
| **4** | **Settlement-position & reconciliation workbench** — extend API to carry settled, reserved, blocked and pending items with source/freshness, then derive intraday liquidity and exception/reconciliation views. | Central-bank and treasury users need usable liquidity, not credit ceiling alone; reconciliation exceptions are a meaningful next workflow. | **L** (domain/API persistence and data migration, ledger semantics, UI, invariant tests) |
| **5** | **Role-specific guided demo scenarios** — seeded end-to-end narratives per persona (e.g. DMO draft auction, bank bid, custodian evidence, auditor review, executive dual approval), with resettable fixtures and visible “simulation” badges. | Makes the broad module set understandable and repeatable for product demos without requiring a trainer or real counterparties. | **M** (scenario fixtures, state reset/service, walkthrough UI and smoke tests) |
| **6** | **Responsive institutional workstation and true mobile account view** — compact nav/sidebar at phone widths, expose Account Overview in mobile surface, responsive summary tiles and accessible horizontal data tables. | People should be able to reach the same account context on a phone; prior playtest showed 390px shell clipping and mobile route is a different dashboard. | **M** (app-shell CSS/layout, mobile routing, device playtest) |
| **7** | **Participant mandate and data-access registry** — model verified institution, users, capabilities, account scopes, expiry and evidence; show least-privilege effective access, revoke sessions and record delegated authority changes. | Institutional operations depend on clear mandate and scope, not a persona title or hardcoded read-only credential. | **L** (identity/mandate model, secure backend enforcement, audit history, threat modeling) |

### Top Two
1. Persona-safe, source-of-truth demo workspaces.
2. Evidence-backed operational status and data provenance.

### Cold-Start Build Brief for #1
1. Inventory all eight personas, sections, action callbacks and APIs; define an explicit capability matrix (`view`, `create-draft`, `submit`, `approve`, `admin`) rather than relying on clearance strings.
2. Distinguish three modes in the type system and UI: a public sandbox preview, actual authenticated session, and unavailable production. Remove “auto authenticated Super Admin”; make login/test portals visibly sandbox-only. Production is disabled until a configured trusted backend/credential flow exists.
3. For the sandbox only, map personas to a curated home and navigation set: Central Bank policy/liquidity, commercial bank accounts/dealer activity, custodian evidence/collateral, DMO issuance, manager positions/RFQ, auditor read-only evidence, executive approval inbox, platform operations. Global Admin gets all modules. Hide inaccessible routes and guard route callbacks as well as buttons.
4. Make persona preview a clearly labeled simulator with a banner, reset action and no change to actual session claims. Existing “Switch Role” becomes “Preview as demo persona”; it may never set `authenticatedPersona` or imply authentication.
5. Consolidate mobile approval and account state on one typed source. Remove static €2.45m fallback when accounts are empty; derive pending badges from the same approval records rendered below. Label static scenario tickets as fixtures and disable them from submit/approve paths unless explicitly in a resettable scenario.
6. Write component tests for menu allow/deny and badges; add browser smoke paths for all seven retained personas and assert forbidden controls/routes are absent, empty-data counters agree, production selection cannot enter demo workflows, and sandbox labels persist through navigation.
7. Definition of done: all seven retained personas launch to intended workspace, mobile/tablet remain device presentation modes rather than personas, all displayed figures name source/environment/as-of time, Auditor cannot see/invoke writes in preview policy, switching preview never upgrades real authority, and every mutation remains server-authorized (or disabled as simulated-only).
